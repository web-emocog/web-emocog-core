# Переиспользование кадров и стоимость инференса

## Что уже общее

В сессии один основной обработчик получает результат FaceLandmarker.
Взгляд, глаза, моргания, положение головы и FACS используют этот результат,
а не запускают отдельный детектор лица для каждого показателя.
ЧСС и дыхание получают пиксели того же кадра через transient WeakMap.
Рабочие потоки и экземпляры моделей создаются при подготовке, не на каждом кадре.

FaceLandmarker, сегментация и модель корпуса решают разные задачи. Их нельзя
заменить одним вызовом без изменения метода измерения. Также нельзя положить
все синхронные детекторы в один Worker и считать это оптимизацией: тогда
основной анализ будет ждать вспомогательные задачи. Вызов `detectForVideo`
синхронный; отдельные Workers защищают интерфейс от его блокировки.
См. [документацию MediaPipe](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js).

## Изменение пути вспомогательных кадров

Прежний путь:

```text
камера -> ImageBitmap -> Worker лица -> ImageData
                                        |-> ЧСС/дыхание
                                        |-> новый ImageBitmap -> вспомогательный Worker
```

Новый путь для уже имеющегося `ImageData`:

```text
камера -> ImageBitmap -> Worker лица -> ImageData
                                        |-> ЧСС/дыхание
                                        |-> structured clone -> вспомогательный Worker
```

Убрано промежуточное создание bitmap для сегментации и корпуса. Для видео,
canvas и остальных источников сохраняется прежний путь. Лицо по-прежнему
получает bitmap; веса, параметры моделей, частоты и пороги не меняются.

Это не передача без копирования: ImageData копируется между потоками. Его
общий буфер нельзя включать в transfer list, иначе он отделится от основного
потока до использования другими потребителями. Такое поведение описано в
[документации transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects).
Сохраняются single-flight, ограничение очереди, capture timestamps и teardown.
Сырые пиксели не добавляются в session JSON, checkpoint, отчёты или API.

В потоке лица импорт `getFramePixels` перенесён из кадровой ветки в подготовку.
Раньше файл тоже не скачивался заново на каждом кадре: браузер кеширует модуль.
Убраны повторные асинхронные обращения, а не повторная загрузка весов.

## Что нельзя безусловно кешировать

- Результат модели между разными кадрами: устаревшие данные нельзя выдавать
  за новое измерение или использовать для фиктивного роста FPS.
- Результат разбора mutable объекта только по его ссылке: обновлённые поля
  иначе могут получить старые QC или gaze признаки.
- Общий пиксельный буфер без явного владения: переиспользование до окончания
  потребителей смешает кадры и временные метки.
- Состояние трекера или FACS между сессиями: это нарушит индивидуальную
  подготовку и независимость участников.

## Следующие направления

1. Отделять стоимость захвата, передачи, модели, возврата и производных
   расчётов. Не оптимизировать небольшие JS-циклы вместо доминирующего инференса.
2. Для GPU/CPU и другого формата входа сначала проверять одинаковые кадры,
   полные результаты и правила качества, затем несколько парных прогонов.
3. Убирать необязательные преобразования и отрисовку, но не снижать скрыто
   частоты измерительных каналов и не менять число принятых проб.
4. Более крупный перенос физиологии в Worker рассматривать отдельно:
   размещение её в потоке лица может замедлить основной детектор. Общий буфер
   потребует протокола владения и отдельной оценки безопасности/совместимости.

Уменьшение числа вызовов не гарантирует рост FPS: важны последовательный
критический путь, синхронизация CPU/GPU, фактическая подача кадров и фоновые
процессы. Замеры на файловом адаптере не равны приёмке физической камеры.

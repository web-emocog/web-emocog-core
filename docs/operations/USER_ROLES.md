# Аккаунты и роли: инструкция оператора

Сверено с runtime-кодом 2026-09-04. Это инструкция по существующим возможностям,
а не изменение ролей на сервере. Роли сайта не связаны с IAM-ролями Yandex Cloud,
GitHub или Linux. У аккаунта одна глобальная роль; доступ к исследовательским
данным дополнительно ограничивается организациями и проектами.

## Первый platform-admin из существующего аккаунта

`developer` не может сам повысить себе права через сайт. Первого администратора
назначает уполномоченный оператор штатной командой `admin:bootstrap`.
Она уже входит в API-образ; выкатывать изменения бэкапов для этого не нужно.

На VM, где работает `wecog-api-1`, подставить точный email **уже существующего**
аккаунта вместо `YOUR_EXISTING_ACCOUNT_EMAIL` и выполнить:

```bash
sudo docker exec \
  --user 10001:10001 \
  --workdir /app/apps/api \
  --env BOOTSTRAP_ADMIN_EMAIL='YOUR_EXISTING_ACCOUNT_EMAIL' \
  --env BOOTSTRAP_ADMIN_PASSWORD= \
  wecog-api-1 npm run admin:bootstrap
```

Команда меняет роль найденного аккаунта на `admin`. Пустой
`BOOTSTRAP_ADMIN_PASSWORD` сохраняет существующий пароль. Если email не найден,
новый аккаунт без пароля не создаётся: операция завершается ошибкой. Не добавлять
пароль в командную строку, историю терминала, чат или Git.

После сообщения `Platform administrator ready` выйти из сайта и войти снова:
команда увеличивает `token_version`, поэтому старые сессии входа отзываются.
`admin` сохраняет доступ к техническим экранам; отдельная роль `developer`
для этих экранов ему не нужна.

Открыть [Аккаунты и роли](https://wecog.ru/apps/web/developer/accounts.html).
Если требуется вход, использовать
[страницу входа](https://wecog.ru/apps/web/developer/login.html).
Не понижать роль единственного platform-admin: отдельного запрета на удаление
последних административных прав в текущем runtime нет. Для обычной работы лучше
использовать отдельный аккаунт с ограниченными правами.

## Изменить существующего пользователя

1. В разделе **Существующие пользователи** найти аккаунт по email/имени и нажать
   **Обновить**, если список не обновился.
2. В строке пользователя выбрать **Role**.
3. Указать нужные **Org IDs** и **Project IDs** через запятую, согласно таблице
   ниже. Это числовые ID из базы, не названия и не slug.
4. Нажать **Save** и дождаться сообщения об успешном сохранении.
5. После изменения роли попросить пользователя выйти и войти заново.

**Save заменяет весь список доступов**, а не дописывает выбранные ID к прежним.
Нельзя случайно очищать организации/проекты, доступ к которым нужно сохранить.
Каждый назначенный проект должен принадлежать одной из назначенных организаций.

Посмотреть соответствие ID и названий можно в том же браузере после входа как
`admin`, открыв защищённые read-only API:

- [Организации](https://wecog.ru/api/organizations): поля `id`, `name`.
- [Проекты](https://wecog.ru/api/projects): поля `id`, `name`, `organization_id`.

Токены копировать не нужно: используются cookies текущего входа. Если API вернул
`401`, сначала войти снова. Не подставлять примерные ID: использовать только
фактически существующие записи. Несмотря на подпись «опционально» у поля Org IDs
в форме, сервер требует эти ID для исследовательских ролей.

## Какую роль выдавать

| Роль | Назначение | Необходимый доступ |
| --- | --- | --- |
| `admin` | Управление всей платформой и аккаунтами всех организаций | Memberships для доступа не требуются; особо привилегированная роль |
| `org_admin` | Управление назначенными организациями, их проектами и пользователями в допустимой области | Хотя бы один Org ID; проекты организаций подбирает сервер |
| `PI` | Руководитель исследований с управлением в явно назначенных проектах | Org IDs и Project IDs; назначает platform-admin |
| `researcher` | Создание проектов, протоколов, приглашений, работа со стимулами, аналитикой и экспортом | Org IDs и хотя бы один Project ID при назначении роли |
| `analyst` | Просмотр данных, аналитика и экспорт без изменения протоколов | Org IDs и Project IDs |
| `assistant` | Просмотр и работа с сессиями, без аналитики/экспорта и редактирования протоколов | Org IDs и Project IDs |
| `developer` | Технические экраны без доступа к данным организаций/проектов | Без memberships; email должен быть в developer allowlist, назначает platform-admin |
| `respondent` | Обычный зарегистрированный пользователь без staff-доступа | Staff memberships не требуются; участие определяется приглашением |

Для автора исследований обычно достаточно `researcher`, для администратора
конкретной организации — `org_admin`. Не выдавать `admin` только ради возможности
создать протокол. Администратор организации не может повышать себя до `admin`,
назначать `PI/developer` или управлять аккаунтами за пределами своего tenant scope.
Непривязанный новый аккаунт первоначально назначает в организацию platform-admin.

## Новые аккаунты

- Самостоятельная регистрация всегда выдаёт `respondent`. Ни email, ни запрос
  браузера не должны автоматически превращать пользователя в сотрудника.
- Уже зарегистрированного человека назначить через **Существующие пользователи**.
- Если аккаунта ещё нет, в **Создать учетную запись** заполнить email, пароль
  минимум 12 символов, роль и обязательные ID, затем **Создать аккаунт**. Передать
  пароль отдельно по защищённому каналу. Не создавать дубликат существующего email.
- Изменения хранятся в PostgreSQL, а не в контейнере: обычный релиз приложения
  их не сбрасывает. Восстановление старой копии БД может вернуть старые назначения;
  после аварийного восстановления права нужно проверить отдельно.

## Источники истины

- `apps/api/scripts/bootstrap-admin.js`: первое назначение platform-admin.
- `apps/api/security/permissions.js`: операции ролей и tenant scope.
- `apps/api/routes/auth.js`: создание аккаунтов, смена ролей и memberships.
- `apps/web/developer/accounts.html`: текущая форма управления.
- [Матрица авторизации](../api/authorization-matrix-v1.md).

Прямые SQL-правки production, обход проверок и изменение browser localStorage
для повышения роли не нужны и не являются поддерживаемой процедурой.

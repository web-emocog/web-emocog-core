# Самостоятельная регистрация wecog

Новая регистрация выключена по умолчанию. Существующие учётные записи
продолжают входить обычным способом. Прохождение эксперимента по ссылке
не требует создания аккаунта исследователя.

## Локальный запуск

Нужны Node.js 22+, зависимости API и отдельная база PostgreSQL 16 на
`127.0.0.1` с именем, оканчивающимся на `_dev` или `_test`.
В `apps/api` примените миграции к этой базе (`DATABASE_URL`, затем
`npm run migrate:up`). Запустите:

```sh
IDENTITY_LOCAL_DATABASE_URL="$DATABASE_URL" npm run identity:local
```

Команда поднимает API и нужные страницы на `127.0.0.1:3000`.
Регистрация открывается в `/apps/web/account/signup.html`.
Письма не уходят в интернет: путь к приватному каталогу JSON-писем
выводится при старте. Используйте тестовые адреса и пароли. В письме
откройте ссылку и подтвердите действие на странице: одно открытие
ссылки не расходует токен. Каталог писем нельзя публиковать или
подключать к веб-серверу; после теста удалите ненужные письма.

## Права и восстановление

- Новый пользователь получает роль исследователя без доступа к чужим данным.
  Организация и первый проект создаются вместе. Владелец назначается только
  внутри созданной организации и проекта, без глобальных прав администратора.
- Приглашение даёт доступ только к указанному проекту. Нужны совпадающий
  подтверждённый адрес и явное принятие; владение почтовым доменом ничего
  не открывает автоматически. Приглашение можно отозвать до принятия.
- Ссылки подтверждения и сброса живут 30 минут; приглашения 48 часов.
  Токены одноразовые, в таблицах проверок хранятся хеши. Очередь доставки
  хранит содержимое писем в зашифрованном виде до отправки или истечения срока.
- Сброс пароля доступен только после подтверждения адреса и отзывает старые
  сессии. Старому пользователю с неподтверждённым адресом сначала нужно
  войти и подтвердить его; если войти невозможно, нужен действующий
  процесс поддержки. Ответы публичных форм не раскрывают наличие аккаунта.

## Включение в production

1. Применить миграции и проверить резервное восстановление в отдельной базе.
2. В Yandex Cloud можно настроить [Postbox](https://yandex.cloud/ru/docs/postbox/).
   Нужны подтверждённый домен отправителя, учётные данные SMTP и записи
   у фактического оператора DNS. Сверить делегирование и настроить
   [DKIM, SPF и DMARC](https://yandex.cloud/ru/docs/postbox/concepts/dns-records)
   без перезаписи уже используемых почтовых записей. Адрес отправителя
   `noreply@wecog.ru` не является входящим почтовым ящиком.
3. Сохранить секреты SMTP и стабильный 32-байтный ключ очереди в защищённой
   конфигурации. Использовать TLS (465 либо STARTTLS на 587).
   Список переменных: `apps/api/.env.example`. Не менять ключ с
   неразобранной очередью: старые сообщения не расшифруются.
4. Сначала проверить на отдельном окружении подтверждение, сброс и
   приглашение с доставкой в реальные почтовые сервисы, а также
   ограничение запросов, срок жизни ссылок и обработку недоставки.
   Только после этого ставить `IDENTITY_ENABLED=true` на публичном сайте.
   Перед открытой регистрацией отдельно определить политику защиты
   от массовых регистраций и рассылки, мониторинг очереди и канал поддержки.

Дизайн ориентирован на [рекомендации OWASP по проверке адресов](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html)
и модель [явного приглашения в рабочую область](https://slack.com/help/articles/201330256-invite-new-members-to-your-workspace).
Настройка локального режима не меняет DNS, Yandex Cloud или production.

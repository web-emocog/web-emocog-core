## Issue 144: Подтверждённые Причины

1. `buildAoiRows` выбирал все презентации по паре block/stimulus и складывал их,
   не связывая с `cognitiveResults.qualityValid`. `buildSessionVisuals` также
   создавал одну карточку на пару, в порядке protocol AOI definitions.
2. Экспорт использовал эти же агрегированные AOI rows и терял presentation,
   attempt, статус и причину исключения.
3. `metricBase` подставлял длительность всей сессии при отсутствии AOI duration.
   Получалась строка без наблюдений с минутами, не относящимися к показу.
4. Summary возвращал exclusions без stimulus/presentation/attempt; UI выводил
   индекс списка исключений как «Проба 1...N». Счётчики зависели от включения
   специальных count metrics в выбранный пакет.
5. Внутри timed block одна логическая проба могла показываться несколько раз
   в одном block attempt. Старый heatmap key не содержал explicit presentation
   ID. Даже добавление ID в UI не разделило бы такие данные без правки producer.
6. Frame context не учитывал presentation ID: поздний результат Worker мог
   попасть в следующий показ той же логической пробы при прочих равных полях.

Воспроизведение до правки: dwell 700 вместо 500 в accepted-only результате,
одна карточка и одна export row вместо двух, missing duration = 60000 ms.
Числа синтетические, не переоценка реальных сессий 116/117.
Логи: `/tmp/wecog-20261102-issues-before.log`.

Важно: суффикс `_0` в ID нормализованной пробы создаётся как индекс repetitions
в таблице, а **не** как номер quality attempt. Нельзя выводить номер попытки
парсингом этого суффикса. Новый интерфейс показывает attempt явно.

## Issue 144: Исправления

- `analytics/attempts.js`: явная связь по presentation ID внутри block/trial/
  stimulus tuple; для старых данных — по полному tuple с attempt. Контексты
  индексируются через Map, а не полным перебором результатов для каждого AOI.
- Статусы `accepted`, `excluded`, `ambiguous`, `incomplete`, `unknown` раздельны.
  Rejected/ambiguous/incomplete не входят в default AOI/group/heatmap aggregates.
  Диагностические карточки и long export сохраняют их, не удаляя evidence.
- Каждая сохранённая презентация имеет отдельную карточку и long AOI rows.
  Передаются ID, block/trial/stimulus, attempt, sourceTrialIndex, presentationIndex,
  начало, статус, причины, `includedInDefault`, `attemptMethod`.
- Причины содержат bounded codes и человекочитаемые ru/en labels; исходные
  Error/stack/произвольные сообщения не отражаются как причины из сервера.
- Новые реальные показы получают session-local sequence в experimentMeta,
  сохраняемый checkpoint. Heatmap учитывает explicit presentation ID; старый
  ключ для samples без ID сохранён для совместимости checkpoint.
- Новый `presentationStartMs` проходит payload validation; schema и TypeScript
  обновлены как optional extension. Повреждённое значение не отражается в error.
- `trialCounts` возвращается независимо от запрошенных metric IDs. Exclusions
  показывают исходную пробу, стимул, показ и попытку, а не индекс списка ошибок.
- Missing AOI duration = null; подтверждённое нулевое наблюдение = 0. Длительность
  всей сессии больше не становится длительностью отсутствующей презентации.
- Если у результата пробы вообще нет gaze samples, создаётся отдельная
  диагностическая запись без вымышленных samples/grid/duration. Статус
  принятия task сохраняется отдельно от отсутствия gaze; такая запись не
  становится наблюдением в default AOI aggregate. Legacy surrogate ID явно
  отличается от записанного ID и не используется для разрезания grid.
- Поздние кадры другого presentation ID отбрасываются до gaze/QC/physiology.

Прежние wire limits 200 gaze presentations и общий бюджет фиксаций не увеличены.
При превышении сохраняется явная truncation/missingness, а не обещание полной
истории. Добавление идентификаторов не отменяет эти ограничения для длинных
timed-протоколов; для кейсов 40 показов с повторами лимит отдельно контролируется.

Исторические записи не переписываются. При сохранённых отдельных presentation
records исправление применяется при чтении после выпуска. Если старый файл уже
необратимо склеил попытки без идентификаторов, их нельзя честно разрезать по
удвоенной длительности: неоднозначность отображается явно. Для legacy records
без статуса сохраняется совместимость с прежним расчётом и метка `unknown`;
это не утверждение, что их качество научно подтверждено.

## Issue 132: Что Установлено И Что Нет

Синтетический тест настоящего `SessionFramePipeline` со stub I/O, источником
30 Hz, быстрым analyzer и контролируемым опозданием browser timers на 4 ms:
старый polling обработал **162/180** доставленных кадров; frame-driven вариант
обработал **180/180**, single-flight = 1. Это воспроизводимый дефект расписания,
не измерение MacBook автора issue и не тест полной ML-нагрузки.

Без задержки таймеров первоначальный тест проходил и на старом коде. Первая
версия стенда также упиралась в отсутствие DOM adapter, а не в расписание;
она заменена VM harness с чистыми I/O adapters до фиксации red result.
Лог достоверного red case: `/tmp/wecog-20261102-scheduler-before.log`.

Исправления:

- Обработка запускается по уведомлению о новом кадре. При занятом analyzer
  остаётся только последний pending frame, без очереди старых кадров.
- Сохранён верхний бюджет 33 ms между стартами; auxiliary strides 3/6/6,
  модели, thresholds и capture/coordinate semantics не менялись. 1000 ms
  heartbeat сохраняет обнаружение полного camera stall без новых кадров.
- Stop/reset отменяет scheduling; поздняя старая generation не меняет новую.
  Fallback без frame observer и immediate retry при смене trial сохранены.
- Отказ публикации camera FPS освобождает busy ownership и использует bounded
  timer retry, а не немедленную рекурсию. Этот negative case проверен отдельно.
- `protocol_qc_*` не накапливаются без активного block attempt и не копируются
  из инструкции как готовая invalidity в новый attempt. Завершённые failed
  attempts/events/repeat evidence не удаляются. Реальное нарушение во время
  активного блока по-прежнему инвалидирует попытку с прежним hold/threshold.
- Сохраняется диагностический `schedulingMethod: frame-notification.v1`.

Порог **25 FPS не понижен**, requested camera rate не выдаётся за доставленные
кадры. Тесты 15/23 FPS не превращают вход в 30; медленный analyzer не проходит
за быстрый. Main-thread fallback может оставаться медленным на слабом устройстве.

Контрольные counts: источник 30 Hz / 180 кадров — обработано 180; 23 Hz / 138 —
138; 15 Hz / 90 — 90. При искусственном analyzer delay 80 ms обработано 73 из
180, не имитируется 25 FPS. Источник работает 6 s, завершение pending работы
разрешено до 6,5 s; max in-flight = 1 и после stop нет pending timers.
Эти цифры сняты дополнительным diagnostic-only запуском того же test body без
изменения исходников продукта: `/tmp/wecog-20261102-scheduler-counts.log`.

Ограничение: нельзя по раздельным замерам утверждать единственную причину
реальных 23 FPS. Нужны одновременные source/callback/analyzed counts, backend,
timings и profiling той же сессии. Issue 132 требует real-device retest и не
закрывается только на основании синтетики. Ни физический предел камеры, ни
точность gaze/ЧСС/дыхания этими тестами не подтверждаются.

Семантика compositor callbacks и missed-frame counter проверена по
[MDN requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback).
Ограничения синхронного inference и Workers описаны в
[официальном MediaPipe guide](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js).
Это обоснование выбора механизма, не доказательство FPS на конкретной камере.

## Дополнительная Проверка Восстановления И Фильтров

В следующем локальном проходе воспроизведены ещё четыре пограничных случая.
Каждый сначала проверен падающим unit test; compatibility case для legacy
unknown остался зелёным до и после изменения.

1. Пока в новой сессии не завершилась даже первая проба, её gaze presentation
   ошибочно получала legacy unknown/included. Теперь сохранённый
   `experimentMeta.presentationSequence` подтверждает новый producer, а
   отсутствие результата означает incomplete/excluded. Номер ID не парсится.
   Старые записи без этой информации не получают вымышленный статус.
2. Runtime уже сохранял `invalidationReason=page_reloaded`, но analytics теряла
   его при пустом qualityIssueCodes. Известная причина теперь попадает в
   карточку, exclusion, JSON/CSV, в том числе без gaze samples. Добавлены ru/en
   подписи. Произвольные invalidation messages не отражаются в ответах, raw

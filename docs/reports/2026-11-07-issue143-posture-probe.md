# Issue 143: постоянная поправка и проверка посадки v9

Этап после локального checkpoint `6c4a974`, ветка `feature/fix_issue_143`.
Основная модель, validation/QC thresholds, API и рабочий протокол не менялись.

## Что делает поправка после калибровки

После 25 точек × 2 клика калибруется ridge. Затем текущая ветка использует
две отдельные серии (`CORRECTION_POSITIONS`, `BENCHMARK_POSITIONS`):

1. Девять точек для кандидата на остаточную поправку. Из медианных ошибок
   по точкам рассчитывается **один** ограниченный вектор X/Y. Это не новое
   обучение ridge и не индивидуальная коррекция каждого участка экрана.
2. `fitValidationCorrection` требует улучшения на fit-серии и допуска
   по leave-one-target-out: улучшить RMS, не ухудшить median/P95 и не
   ухудшить ни одну исключённую цель больше чем на 1 px. Плохая абсолютная
   точность сама по себе не включает поправку; хорошая абсолютная точность
   не запрещает её, если остаточный общий сдвиг устойчиво устраняется.
3. Пять других точек проверяют уже рассчитанный кандидат против raw на тех
   же наблюдениях. Они не входят в fit. Поправка остаётся, только если
   средняя ошибка уменьшается, разброс ошибки не выходит за допуск и
   величина среднего bias не растёт; иначе выполняется rollback.

Код: `apps/participant-web/js/gaze-tracker/{validation-metrics,bias-correction}.mjs`,
участник: `apps/participant-web/js/web-page/tests-updated.js`.
Вектор прибавляется к `corrected`, не к `raw`. Он не обновляется после
каждого стимула, при смене посадки или по данным будущего испытания.

В human v8 ни у одной модели поправка не прошла первый допуск. Например,
у full patch RMS по исключённым целям снизился с 62.3 до 43.6 px, но две
цели стали хуже; у Gradient All — три. Поэтому v8 измерял не влияние
поправки, а изменения замороженных моделей с `raw=corrected`. Даже если
постоянная поправка прошла стартовую проверку, это не означает, что она
компенсирует изменившийся позже bias. Нельзя вычитать оценённый по конечным
контрольным целям вектор из будущих сессий.

## Что добавлено в v9

Отдельный localhost-режим `?models=gradient&pose=1`, не новый predictor.
Те же четыре модели v7/v8, один camera/analyzer loop, общий subset
калибровочных кадров, те же correction/rollback. После одного fit и
независимой проверки коррекции показываются три серии:

- `natural`: исходная удобная посадка;
- `lowered`: немного ниже в кресле, без изменения окна или камеры;
- `returned`: возврат к исходной посадке.

Перед каждой серией цели скрыты до явного нажатия кнопки. Через 60 s без
нажатия тест останавливается и освобождает камеру; Stop/Escape/resize/уход
со страницы используют тот же teardown. Во всех сериях 5 одинаковых точек,
не использованных ни в fit, ни в решении о коррекции, с теми же 1000 ms
settle и 2000 ms сбора. Между сериями модель, gate и поправка заморожены.
Четырёхминутного ожидания нет. Рабочий 40-trial блок не затрагивается.

Отчёт `issue143_eye_gradient_pose.v9`:
`poseProbe.stages[{id,rows}]`, отдельные raw/corrected summaries, counts,
off-screen predictions, head/eye proxies по окнам. Не v8 `before/after` и
не измерение длительного дрейфа. Raw video, кадры глаз, landmarks, веса,
ряды gaze или новый запрос к API не добавлены. Действует явное разрешение
камеры по кнопке. Экспорт только после teardown, имя
`wecog-issue143-eye-gradient-pose-v9.json`.

При анализе сопоставлять одни цели во всех трёх сериях. Сравнивать signed
bias B−A1 и A2−A1, spread, пропуски и baseline head proxies. Возврат
прогноза ближе к A1 одновременно с возвратом pose proxy поддержит
гипотезу о посадке, но не докажет причину сдвига v8. Если изменение позы
не видно в proxies, либо возврат/покрытие недостаточны, не объявлять
устойчивость. Это self-instructed movement с возможным order/time effect,
не физически измеренный угол головы и не motion benchmark на выборке.

URL: `http://127.0.0.1:4203/apps/autotests/manual/issue143-gaze.html?models=gradient&pose=1&rev=20261107-143k`.
Сервер из корня: `python3 apps/autotests/scripts/serve-static.py 4203`.
V7/V8 сохраняют прежние сценарии и форматы. Rollback — отдельный revert
локального v9 и его тестов; не трогать checkpoint, модель или сессии.

## Проверенный следующий кандидат: within-click loss (отклонён)

Гипотеза: усреднение calibration frames скрывает нестабильные направления
eye appearance. Если считать squared loss на всех принятых кадрах одного
клика с равным весом **каждого клика**, его можно точно записать как
`(w·mean+b−target)^2 + wᵀcovariance·w`. Это не head→target regression:
head/pose и контрольные цели не входят в fit. Положение головы не выводится
из covariance; часть разброса может быть настоящим движением глаз/шумом.

Оригинальный offline fit:
`scripts/reference-data/issue143-click-scatter.mjs`. До 50 mean/covariance
rows, до 30 кадров на клик, до 120 признаков; covariance в packed triangular
Float64Array. Стандартизация только train-fold, оба клика target group
исключаются вместе. λ `[.01,.1,1,10,100]` выбирается по ошибке **кадров**
исключённых calibration groups, не только mean. Cholesky возвращает null
при численном провале, не нулевую модель. Production fit/feature extractor
не менялись; никакой импорт этого скрипта в браузерный participant flow
не добавлен. На пользовательских features fitter не запускался.

Методологический контекст: [Bishop, 1995](https://www.microsoft.com/en-us/research/publication/training-with-noise-is-equivalent-to-tikhonov-regularization/)
обсуждает связь шума и регуляризации; [Severitt et al., 2023](https://bop.unibe.ch/JEMR/article/view/9261)
исследуют noise-sensitive calibration fitting. Просмотрены первичные
страницы/abstract; новые формулы выведены для линейного squared loss,
не скопированы из implementation этих работ. Новых dependencies/weights/
datasets нет, код под Apache-2.0 репозитория. Результаты статей не являются
доказательством точности EmoCog.

`node scripts/reference-data/issue143-scatter-synthetic.mjs`: 25 искусственных
targets × 2 клика × 6 кадров. Две training conditions (идентичные кадры;
небольшое изменение lid pixels), 16 иных targets × 6 predictions на каждом
из 9 measurement conditions. Оба fit видят одинаковые calibration captures,
test validity задаётся **одним прежним full-patch gate**. Raw, без correction,
отдельно missingness, spread и 8 off-screen-truth случаев. Это exploration,
не физическая модель век/посадки или webcam acceptance.

Результат при небольшом разнообразии training lid pixels:

| Условие | Mean-only error, px | Within-click error, px |
| --- | ---: | ---: |
| Normal | 18.51 | 23.87 |
| Lid ±.04 widths | 691.55 | 1158.96 |
| Lid +.08 widths | 1320.13 | 1648.61 |
| Partial aperture | 96.32 | 92.37 |
| Glare | 36.48 | 41.61 |
| True-gaze jitter | 20.33 | 25.20 |

Все 96 predictions/condition приняты; ухудшение не скрыто изменением gate.
При lid ±.04 off-screen predictions на экранных целях 72 → 96. Малое
улучшение partial-aperture и некоторых extreme случаев не компенсирует
регрессии. При отсутствии within-click variation результаты совпадают
с прежним loss в пределах округления прогноза. Фит двух вариантов вместе
в данном Node micro-run занимал около 0.66–0.72 s, включая рендер training
images/выделение признаков; это не чистое время Cholesky или latency.

**Решение: не подключать кандидат к участнику и не просить новый human run
ради него.** Колебания внутри одного короткого клика не покрыли новое
изменение appearance между посадками. Включён отрицательный regression test
на этот failure. Для движения дальше требуется изменение представления
eye geometry/appearance либо более разнообразные calibration observations,
с отдельным контролем, чтобы не потерять настоящее перемещение глаз и
off-screen specificity. Нельзя ограничиться подавлением jitter или отказами QC.

включая 5 новых на moment fit/численные провалы/negative image oracle и 2

Предшествующие browser результаты выше относятся к реализации v9, её код

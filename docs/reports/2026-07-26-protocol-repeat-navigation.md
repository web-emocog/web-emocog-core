## Техническая схема повторов

1. На старте пробы сохраняется снимок активных invalidating issues.
2. На завершении пробы объединяются активные в начале, возникшие в интервале и оставшиеся активными ошибки.
3. Результат получает `qualityValid`, `qualityIssueCodes` и `qualityIssues`.
4. `SessionStateMachine` сохраняет в repeat queue только `trialId` незасчитанных проб и причины.
5. Cognitive runner формирует новый plan из этих `trialId`, не повторяя валидные пробы.
6. Checkpoint хранит repeat queue; старые checkpoint без `issues` восстанавливаются безопасно.

## Принятые решения

- Ошибка сети не инвалидирует локально записанную пробу.
- Краткие движения головы и краткие просадки FPS не создают повтор.
- Повтор ограничен тремя попытками, чтобы исключить бесконечный цикл.
- Figma connector не вернул design node (`INVALID_ARGUMENT`), поэтому маршруты сверены с сохранённой в репозитории UX-спецификацией той же архитектуры.

## Rollout и rollback

1. Web и participant static нужно выпускать одной версией, поскольку cognitive runner использует новый `trial-quality.mjs`.
2. Service worker/CDN cache для participant assets необходимо инвалидировать.
3. Миграции БД для этой правки не требуются.
4. При rollback вернуть web и participant static вместе. Сохранённые repeat queue обратно совместимы: неизвестные дополнительные поля игнорируются.

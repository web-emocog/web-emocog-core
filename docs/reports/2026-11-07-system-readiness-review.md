# Системная проверка локального кандидата

Обновление от 8 ноября: ветки синхронизированы, исправления блокирующих
рисков и повторные проверки описаны в [новом отчёте](2026-11-08-branch-sync-issues-review.md).
Ниже сохранены результаты исходного прогона, а не статус новой сборки.

7 ноября 2026 года, `feature/signal-quality-profiles`, база `b16ce38`
и накопленные локальные изменения. Production, GitHub и исходная таблица
аудита не менялись. Проверялись изолированные PostgreSQL, контейнеры API
и веб-части, синтетические аккаунты, протоколы, записи и медиа. Физические
камера и микрофон не использовались. Проверка относится к основной
веб-платформе, не к экспериментальным расширениям и Dota-пилоту.

## Вердикт

- **Внутренний стенд с синтетическими данными:** пригоден. Основные
  маршруты исследователя и участника работают, выпуск можно репетировать.
- **Пилот с реальными участниками:** условно не готов. Нужны закрытие
  дефектов согласия и валидности проб, исправление AOI, повторная
  проверка доступа и полная приёмка на проблемных устройствах.
- **Открытая регистрация и оплата:** не готовы. Помимо пилотных
  блокеров нужны реальная доставка писем, эксплуатационная приёмка и
  платёжный контур. Экран тарифа остаётся заглушкой.
- **Научные измерения:** техническая сохранность и воспроизводимость
  отдельных расчётов проверены; точность взгляда, ЧСС, дыхания и мимики
  относительно независимого эталона этим прогоном не подтверждена.

## Исправлено

1. **Критично для доступа к данным.** Числовой ID строки и текстовый ключ
   сессии авторизовывались одним условием, а затем маршрут выбирал только
   один из них. На изолированном HTTP-стенде коллизия дала 200 на чтение
   чужого участника и 200 на остановку чужой записи. Теперь чтение
   проверяет права на ту же строку, которую возвращает, а остановка
   обновляет только доступную запись с точным текстовым ключом.
   Защищён и повторный старт. Регрессия проверяет оба направления
   коллизии, 404 для чужого, неизменный статус чужой строки и нормальный
   доступ к своей записи.
2. **Ограничение видимости сотрудников.** Руководитель видел ID всех
   проектов сотрудника, даже если имел доступ только к одному из них.
   Список теперь возвращает только общие проекты. Полный список
   сохраняется для администратора платформы. Проверено на двух
   организациях и сотруднике с доступом в обе.

## Открытые риски

| Приоритет | Риск | Доказательство и критерий закрытия |
| --- | --- | --- |
| Высокий | Нет серверной гарантии квитанции согласия | Реальный API выдал токен и принял промежуточную запись с HTTP 200 без квитанции; в БД ноль квитанций. Для новых внешних сессий проверять квитанцию и версию документа до резервирования запуска и записи данных. Определить отдельный режим для синтетики и правила для исторических записей. |
| Высокий | Блокировка медиа при бэкапе занимает общий пул | Под эксклюзивной блокировкой 20 запросов с несуществующими кодами заняли 20 соединений; readiness завершилась только после снятия блокировки. Нужны ранний отказ неверных кодов и ограничение числа ожидающих/времени ожидания даже для действующих приглашений; прогон при фактическом бэкапе на объёме стенда. |
| Высокий | Видео может оборваться после показа, но проба засчитывается | Независимая проверка: поздний decode error после resolve play не вызвал обработчик отказа; таймер ответа остался. Событие сбоя после начала должно пометить только это предъявление как технически прерванное, не как ошибку участника. |
| Высокий | Пропуск повреждённого стимула загрязняет здоровые пробы | Независимый прогон машины состояний: активная ошибка остаётся после Skip, следующая исправная проба попадает в повтор и следующий блок наследует ошибку. Ограничить ошибку предъявлением; проверить пропуск, повтор, последующий блок и отсутствие дублей. |
| Высокий | Пропуски взгляда превращаются в промахи AOI | Контрольный расчёт: одно попадание даёт 100%, предъявление без наблюдений отдельно даёт no_data, вместе получается 50% computed. Для процента достижения отделить наблюдаемые предъявления от отсутствующих данных, показывать знаменатель и покрытие; версионировать метод и проверить воспроизводимость выгрузки. |
| Средний | Сброс фильтров смешивает версии публикации | Независимый тест состояния: после Reset выбрана новая версия, но ID сессии и набор метрик остались от старой; запрос даёт пустую выборку. При смене версии атомарно пересобирать доступные сессии и показатели. |

Свободный текст опросов нельзя считать автоматически обезличенным;
для пилота нужны правила его использования и выгрузки. Репетиция
бэкапа подтверждает целостность файлов и базы, но не гарантирует,
что восстановление старого снимка автоматически учтёт последующие
удаления. Это отдельная эксплуатационная проверка перед переездом.

## Сильные стороны

- Публикация отделена от черновика. Постоянная ссылка открывает
  актуальную публикацию, существующая сессия остаётся на своей версии,
  медиа в отчёте привязано к исходной версии стимула.
- Сохранение устойчиво к потере соединения и ответа после записи:
  повторная отправка не создаёт дубль. Есть локальная точка
  восстановления, учёт прерванных попыток и явные статусы данных.
- Закрытые входные схемы, проверка ролей и принадлежности к проекту,
  отзыв сессий после смены пароля, квоты и изолированный конвейер медиа
  имеют живые HTTP/SQL-тесты, в том числе отрицательные.
- Исследовательские выгрузки, привязка к выборке и версионность
  измерений уже есть. Риски AOI и сброса фильтров локальны, но могут
  исказить вывод или скрыть данные, поэтому важны для пилота.
- Поставка ограничена явным списком статических файлов, образы
  проверяются отдельно, восстановление БД и файлов воспроизводимо.

## Программа приёмки

1. Закрыть шесть открытых рисков, проверять сбои на живых API/БД,
   отсутствие данных не считать наблюдённой ошибкой участника.
2. Собрать согласованную пару API и frontend, повторить CI, нагрузку
   с одновременными бэкапом, загрузкой и прохождением, восстановление с
   проверкой удалений. Проверить мониторинг и откат на отдельном стенде.
3. На проблемных устройствах пройти короткий и длительный протокол
   в установленном Safari и Chromium/Edge, сверить FPS источника
   и анализа, покрытия, пропуски, причины повторов и итоговый экспорт.
   Инструкция: [ручная приёмка](../operations/real-device-acceptance.md).
4. Для научных утверждений отдельно сверить метрики с синхронными
   эталонными измерениями, опубликовать ошибки и долю пропусков, не
   заменять это локальными тестами.
5. Для открытого продукта проверить реальный SMTP/DNS, доставку и
   повтор писем, поддержку, жизненный цикл данных и согласия. Добавить
   платёжный сценарий, выдачу прав по подтверждённой оплате, отмену,
   возврат и повтор вебхука без двойного начисления.

Прогоны частично пересекаются, поэтому их числа не следует складывать
как число независимых функций. Для повторения сценарии с живыми API
нужно запускать с отдельными конфигурациями и процессами. При совместном
запуске в одном Playwright worker тест смены пароля закрывал общий Node
пул до файла проверки участника (`Cannot use a pool after calling end`).
Выделенный повтор сценариев участника прошёл 21/21. Первый запуск SQL
на хосте не имел ffmpeg, а первый Linux-прогон не мог выполнить тестовые
заглушки из noexec /tmp; финальный запуск прошёл с ffmpeg в контейнере и
исполняемым /tmp только для тестовых фикстур, не для рабочей конфигурации.
Временные контейнеры и учётные данные удалены после прогонов.
